# 多想想

一个问题可以问模型一次，也可以问很多次。每个答案都有它的代价，而如果好答案和坏答案分得清，再试一次就值得花这个钱。

## 算账

<RecipeFor id="reckoning_dataset" />

<ItemLink id="reckoning_dataset" />里是一行行相加的数，写出每一步的累计：

```
> 12,7,30,5
= 19 49 54
```

最后一个数就是答案。每一步都能单独检查，谁都能查，除了算术什么也不用，所以它才值得多想：错的答案能被抓住，再试一个。**算账**测试看练习中从未出现的和里，每一步都对的占多少，服务器给一个问题写够多的答案，就能达到 70%。

## 一个问题的答案数

在[模型服务器](deployment.md)里放一枚<ItemLink id="kv_cache" />，第三个按钮就决定它对一条指令或一道算账写多少个答案。它只留一个：算账留每一步都查得过的；指令留能在沙盒里运行的那些当中最多的结果，面板最后一格放了裁判的话，就留裁判打分最高的。其他问题只问一次。

每个答案都要付钱。它们只读一次问题，然后一起往下写，所以一台 64 宽的服务器，一个问题写 64 个答案的代价是写一个的 23 倍，每秒 26 个回答降到大约一个。换来的是，服务器的界面显示每项测试现在的成绩，而提问的一方都按这些成绩办事。一个问题写一个答案过不了的测试，写三十二个可能就过了。

能不能检查才是关键。一个两块、64 宽的模型，练了 3,000 步算账：

| 一个问题的答案数 | 取最常见的 | 取查得过的 |
| ---------------- | ---------- | ---------- |
| 1                | 15%        | 15%        |
| 2                | 13%        | 24%        |
| 4                | 13%        | 32%        |
| 8                | 16%        | 41%        |
| 16               | 18%        | 50%        |
| 32               | 18%        | 65%        |
| 64               | 15%        | 68%        |

投票几乎没用，因为模型每次错的往往是同一个地方。检查不管一个答案出现过多少次。

指令就不一样了，没有什么能检查本意。一个微调过的模型，只写最可能的答案时，77% 符合本意；抽 16 个答案取多数，只有 68%，尽管这 16 个里有正确答案的情况占 73%。服务器对指令想得更久，可能反而过不了程序测试，它的界面会说明。

## 给每一步打分

[调校台](tuning.md)设为验证、检查*算账*时，按每次尝试对了多少步来打分，而不只看最后对不对，所以四步对三步的尝试，比一步都不对的更值钱。除此之外没有东西告诉它答案。在同一个模型上以 0.0003 练 200 步，它尝试的步骤里对的比例从 49% 升到 62%，第一次就算对的从 12% 升到 27%。之后一个问题写 32 个答案能到 75%，写 64 个到 77%，写一个只有 19%。

## 化验

炉温稳在那一档的熔炼会给出一份化验，一行要相加的数。冶炼炉的控制器按服务器提供的形式通过了[精准](tuning.md)和算账，它就把化验交给这个控制器。每一步都对，这次熔炼一份矿石就出九个锭，而不是六个。服务器为此花了多少，在它的界面上归在冶炼炉名下。
